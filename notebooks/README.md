# notebooks

色によるグループ分けの精度を測って上げるための、marimo ノートブック置き場です。
**Python だけで完結**していて、pnpm ワークスペース（`apps/*` と `packages/*`）の外にあります。
アプリのビルドや CI には一切関与しません。

## 必要なもの

- [uv](https://docs.astral.sh/uv/)

## 使い方

```bash
cd notebooks
uv sync                            # 依存のインストール（初回のみ）
uv run marimo edit palette_lab.py  # 編集モードで開く
uv run marimo run palette_lab.py   # 閲覧モードで開く
uv run pytest                      # tests/ のテスト（写真もネットワークも不要）
```

## 構成

```
notebooks/
├─ palette_lab.py                 marimo ノートブック
├─ src/dragonfly_lab/
│  ├─ palette.py                  現行アルゴリズム（packages/core/src/palette.ts の移植）
│  ├─ methods.py                  精度を上げるための候補手法
│  ├─ cases.py / evaluation.py    正解データでの採点
│  ├─ remote.py / images.py       写真の取得・キャッシュ・前処理
│  └─ display.py                  表に埋め込むサムネイルとパレットの帯
├─ tests/
│  ├─ case.json                   手書きの正解（同じ組に入ってほしい写真）
│  └─ test_lab.py                 合成画像だけで回るテスト
└─ remote/                        取得したサムネイルのキャッシュ（gitignore 済み）
```

`palette.py` は `packages/core/src/palette.ts` の移植です。移植した時点（2026-07-31、実写 40 枚）で、
**代表色の hex が完全一致し、距離の差が 1e-16 以下**であることを TypeScript を直接実行して確認しました。
乱数（k-means++ の初期中心）まで再現してあります。

その確認に使った TS ブリッジは削除したので、いま自動で再検証はされません。代わりに、確認できた
時点の出力を `tests/golden_palettes.json` に固定してあります（`uv run pytest` で照合）。
`palette.py` を書き換えるとこのテストが落ちるので、「現行アルゴリズム」からずれたことに気付けます。
本番側 (`palette.ts`) を変えたときは、こちらも直してゴールデンを作り直してください。

## 入力画像とキャッシュ (`notebooks/remote/`)

入力は本番 API (`GET /api/v1/users/me/photos`) から取ってきた自分の写真です。

初回だけ API キー（Web の設定画面で発行する `dfly_...`）が要ります。ノートブックのパスワード欄に
貼って「リモートから取得」を押すと、サムネイルが `notebooks/remote/` に保存されます。

```
notebooks/remote/
├─ index.json                撮影日時とワールド名（並び順もこれで決まる）
└─ <photoId>.avif            サムネイルをそのまま保存したもの
```

**2 回目以降はこのディレクトリを読むだけで、API は叩きません。** 取り直したいときは、もう一度
「リモートから取得」を押す（キャッシュを丸ごと置き換えます）か、ディレクトリを消してください。

- キャッシュは `.gitignore` 済みです。自分の写真がリポジトリに入ることはありません。
- marimo が保存するのはセルのコードだけで UI の入力値は保存しないため、API キーがファイルに残ることもありません。
- 呼ぶのは読み取り (GET) だけなので、写真が変更・削除されることはありません。

### Cloudflare の Error 1010 が出るとき

urllib の既定の User-Agent (`Python-urllib/3.x`) は Cloudflare の Browser Integrity Check に
弾かれ、API に届く前に 403 (Error 1010) になります。そのため `remote.py` の `_USER_AGENT` で
`dragonfly-notebooks/0.1` を名乗っています。また、API キーが無効なときは 401 ではなく
**403 + `{"error": "Invalid API key."}`** が返ります（Cloudflare の 403 とは本文で区別しています）。

## 正解データ (`tests/case*.json`)

「この写真たちは同じグループに入ってほしい」という組を並べたファイルです。手で書くので、
末尾のカンマは許して読みます。`tests/case*.json` に置いたものはノートブックの
「採点に使う正解ファイル」で選べます。

| ファイル | 中身 |
| --- | --- |
| `case.json` | 手で書いた正解。**手法を選ぶときに使ったもの** |
| `case-2.json` | キャッシュ 200 枚を目で見て作った 27 グループ。**選定には使っていない**ので、過学習していないかの確認に使えます |

```json
[
  ["019fa429-...", "019fa42a-...", "019fa42a-..."],
  ["019fa42d-...", "019fa162-..."]
]
```

採点は 3 つの指標で行います。

| 指標 | 中身 | なぜ見るか |
| --- | --- | --- |
| 手書き | `case.json` のケースが 1 つの組に収まったか | 本命。ただし数が少ない |
| 自動 | 同じワールドで 5 分以内に撮った写真同士が同じ組に入った割合 | 数が多く、手書きへの過学習を防ぐ |
| 純度 | 同じ組のペアのうちワールドまで一致した割合 | まとめすぎ（全部を 1 組にする）の抑え。無作為だと約 2% |

## いちばん効いた手法: 画素の色ヒストグラム

代表色 5 色に潰すのをやめ、**全画素を OKLab の 3 次元ヒストグラム（L を 6、a と b を 10 分割 =
600 bin）にして Hellinger 距離で比べる**のが、現時点で最良でした（`histogram.py`）。
まとめ方は今までどおり average linkage + 大きい組の再分割です。

1 グループ 7 枚を目標にしたとき（200 枚 → 29 組、正解 29 ケース）:

| 手法 | 完全一致 | ペア | 自動 | 純度 | 最大組 | 時間 |
| --- | --- | --- | --- | --- | --- | --- |
| 現行 `kmedoids/greedy/area/L=1` | 9/29 | 41% | 36% | 7.9% | 32 | — |
| パレット EMD `average/emd/accent/L=0.5` +再分割 | 17/29 | 68% | 65% | 20.5% | 14 | 2.9s |
| **色ヒストグラム +再分割** | **24/29** | **81%** | **80%** | **33.2%** | 14 | **0.7s** |

- 目標 5 / 7 / 10 枚のどこでも順位は変わりません（ヒストグラムが全部で 1 位）
- 手法選定に使っていない `case-2.json` だけで見ても 16/26 → 22/26
- チューニングしていない素の設定（4×8×8 bin）でも 24/29 で、ハイパラ選びで買った勝ちではありません
- 速度もパレット EMD の約 1/4

**なぜ効くのか**: 5 色に潰すと、同じ場所で撮った似た写真でも k-means の切れ目が変わって代表色が
入れ替わることがあります。ヒストグラムは分布をそのまま持つのでその揺れが出ません。Hellinger 距離
（要素ごとに平方根を取ってからユークリッド）は、面積の小さい差し色の違いを効かせます。
L 方向を粗く切ってあるのは、露出や時刻の違いで明るさだけがずれた写真を離さないためです。

**注意**: この勝ちは必ず「再分割あり」とセットです。再分割なしだと最大組が 59 枚になり、
まとめすぎの点ではパレット EMD より悪くなります。

### 本番への反映

この手法は `packages/core/src/histogram.ts` に実装し、Web の `/groups` で使うようにしました
（`PALETTE_VERSION` は 4）。ヒストグラムは `photo_palettes.histogram` に base64 で保存します
（1 枚あたり中央値 120 文字）。同じ写真 200 枚を本番の TypeScript 経路
（抽出 → base64 保存 → 読み戻し → 距離 → グループ分け）に通すと、
完全一致 24/29・ペア 81%・自動 80% とこのノートブックと同じ結果になります。
純度だけ 33.2% → 27.7% と少し下がりますが、これは保存時に uint8 へ量子化する際、
残すと決めた bin に最低値 1/255 を与えているぶんの差です。

## 調べた手法と結果（パレット距離の範囲で）

200 枚・1 グループ 10 枚（k=20）で総当たりしました。差し替えられるのは 3 か所です。

- **対応付け** — `greedy`（現行 / 近い色から 1 対 1）, `hungarian`（最適な 1 対 1）,
  `emd`（色を面積ぶん運ぶ輸送問題として測る）
- **明度の重み** — OKLab の L の差にかける倍率。1.0 が現行
- **まとめ方** — `kmedoids`（現行）, `average` / `complete` / `ward`（階層的）, `spectral`

| 手法 | `case.json`（選定に使用） | `case-2.json`（未使用） | 自動 | 純度 | 最大グループ |
| --- | --- | --- | --- | --- | --- |
| 現行 `kmedoids/greedy/area/L=1` | 1/3 | 11/27 (48%) | 38% | 6.9% | 34 |
| 現行 `kmedoids/greedy/accent/L=1` | 0/3 | 13/27 (47%) | 51% | 5.9% | 36 |
| **推奨 `average/emd/accent/L=0.5`** | **3/3** | **20/27 (82%)** | **83%** | 6.8% | 50 |
| 推奨 + 大きい組の再分割（目標の 2 倍まで） | **3/3** | 18/27 (74%) | 71% | **14.0%** | 20 |

`case.json` は手法を選ぶときに使ったので、そこで満点なのは当然です。**選定に使っていない
`case-2.json` と自動ケースでも同じだけ良くなっている**（11/27 → 20/27、38% → 83%）ことが、
特定のケースに合わせ込んだのではないことの根拠になります。

効いているのは主に 2 つでした。

1. **EMD（輸送問題として測る）** — 1 対 1 の対応付けをやめると、「片方の 1 色が、もう片方では
   2 色に分かれている」写真同士を近いと判定できます。手書きケースを満点にした設定は
   いずれも EMD でした。
2. **明度の重みを 0.5 に下げる** — 同じ場所で露出や時刻が違うだけの写真が、L の差だけで
   遠くなってしまう問題が減ります。0.25〜0.5 の範囲で安定して良く、0（完全に無視）は悪化します。

まとめ方は `average`（階層的クラスタリング）が最良でした。`kmedoids` は代表 1 枚に
引きずられるため、代表がずれると組ごと崩れます。

再分割は「10 枚ごと」に効きます。階層的クラスタリングはありふれた色の写真が 1 つの大きな塊に
なりやすいので、目標の 2 倍を超えた組だけ中で割り直します。自動再現は少し下がりますが、
純度が倍になり、最大グループが目標の 2 倍に収まります。

推奨設定は `dragonfly_lab.RECOMMENDED` にあります。こちらは本番には入れていません
（色ヒストグラムの方が良かったため）。

## 調べたが採らなかった手法

論文まで当たって 4 系統を実装し、同じベンチで採点しました。実装は `src/dragonfly_lab/cand_*.py` に
そのまま残してあります（調査の記録なので、本体からは参照していません）。

| 系統 | 試したもの | 結果 |
| --- | --- | --- |
| `cand_transport.py` | Sinkhorn / partial OT / unbalanced OT / ロバスト地上コスト (Rubner 飽和・Pele-Werman 閾値) / SQFD | 閾値付き地上コストで 23/29 まで改善。ただし最大組 44 でまとめすぎが直らない |
| `cand_descriptor.py` | OKLab 3 次元ヒストグラム / 色モーメント / Color Layout / MS-SWD | **採用**（上記） |
| `cand_graph.py` | k-reciprocal 再ランキング / 拡散距離 / 相互 kNN + コミュニティ検出 | ヒストグラムに重ねると 24/29 まで届くが、単体のヒストグラムに勝てず手数だけ増える |
| `cand_cluster.py` | size-constrained k-means / 容量制約付き割当 / HDBSCAN / balanced cut | 数字は最高 (25/29) だが目標枚数を無視するため「1 組およそ N 枚」に応えられない |

「1 色だけ大きく食い違うせいで似た写真が遠くなる」を抑える方向（ロバスト地上コスト、partial OT）は
どれも効きました。ボトルネックが**代表色 5 色という表現そのもの**だったので、表現を変えるのがいちばん
効いた、という結論です。
